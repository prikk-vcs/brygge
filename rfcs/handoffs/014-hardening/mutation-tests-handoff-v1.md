# Handoff — RFC 014 D-1…D-3: mutation tests of every untrusted parser (batch M)

**Governing:** RFC 014 D-1, D-2, D-3 and D-5 (accepted 2026-10-17). **Crates:** the four decoders and
`brygge-ir` (test code only), CI, and one `publish = false` test-support crate. **After batch A.**
Independent of batch R. **File one review request,** or two if it grows (M-1: the generator and two parsers;
M-2: the rest and the CI job). Say which.

**The constraints, which are not negotiable** (they are the owner's rulings):
- **stable Rust,** on all four CI platforms;
- **no new dependency** of any published crate, and no new cargo feature or public API: nothing a user can
  see changes;
- **triggers, never a schedule.**

---

## 1. The generator: one place, test-only

- **A small, deterministic pseudo-random generator and the mutation operators,** in **one** place: a new
  workspace member `tools/mutate` (`publish = false`), used by each crate as a **path-only
  dev-dependency**.
  - Cargo drops path-only dev-dependencies when publishing. Prove it with
    `cargo publish --workspace --dry-run --locked`, which must still package all six crates.
  - `tools/check-ir-isolation.sh` must stay green, since dev-dependencies are not in the normal closure.
- **The generator:** a simple, well-known algorithm (for example splitmix64 or xorshift), written out in a
  few lines, with no crate. It is seeded from a fixed constant plus the test's name.
- **A failure must print:**
  - the test;
  - the seed index;
  - the iteration;
  - the operator chain;
  - and **write the mutated input to a file** under the target directory, so it can become a regression test
    verbatim.
- **The operators:**
  - **generic:** flip a bit; set a byte to 0, to 0xFF, or to random; insert, delete or duplicate a run;
    truncate; splice two seeds;
  - **format-aware,** given a list of "interesting positions" each parser's module supplies (offsets of
    length and count fields, varints, delta headers, window sizes, revision numbers, sizes in headers). At
    those positions: write 0, 1, the maximum, `ceiling − 1`, `ceiling`, `ceiling + 1`, and a value that
    overflows 32 or 64 bits when multiplied or added.
  - The format-aware operators are what make this find RUSTSEC-2026-0344's class. **Each parser module must
    supply them.** Random bytes alone are not enough.

## 2. The modules (D-1)

**One `#[cfg(test)]` module per parser,** in the crate it tests. Each one:
- takes its **seeds** from that crate's existing valid fixtures, built by the same helpers the tests already
  use. It needs no network and no external tool for the seeds themselves; where a seed must come from a real
  tool (`hg`, `svnadmin`), commit the generated bytes as a fixture file;
- uses **small `Limits`** wherever the parser takes them, so that the ceilings are near enough for the
  boundary values to hit them;
- asserts, for every mutated input:
  - `Ok`, or a typed error. **A panic fails the test;** use `catch_unwind` so that one input cannot hide the
    rest, then fail with its details;
  - **no `Ok` output larger than the declared ceiling** (the reconstructed text, the decompressed revision,
    the svndiff target, the artifact's blobs);
  - **a per-input time budget,** checked after the call (for example 2 s at the quick depth). A true infinite
    loop is caught by the CI job's `timeout-minutes`; set that explicitly on the job.

| Module | Seeds | Fed through | Interesting positions |
|---|---|---|---|
| `brygge-decode-cvs` `rcs` | the `,v` fixtures | `parse_rcs`, then `contents_of_many` over every revision, and `content_of` on a sample | the `head`/`next`/`branches` numbers, `@`-string lengths, `a`/`d` command counts |
| `brygge-decode-svn` `dumpstream` | the dump fixtures (fulltext, `--deltas`, `svnrdump`) | `parse_dump_with` (small `Limits`), then `decode_with` on small dumps | `Content-length`, `Prop-content-length`, `Text-content-length`, `K`/`V`/`D` lengths |
| `brygge-decode-svn` `svndiff` | the windows from the D-2 tests | `apply(delta, base, max)` | the five window integers, instruction lengths and offsets |
| `brygge-decode-hg` `revlog` | the revlog fixtures (inline and split, zlib and zstd) | the index parse, `decompress`, delta application | `offset_flags`, `comp_len`, `uncomp_len`, `base_rev`, the zstd frame header and block sizes |
| `brygge-decode-hg` metadata | the changelog and manifest texts, obsstore, bookmarks, phaseroots | each parser | the line structure, the length prefixes in obsstore |
| `brygge-ir` `artifact` | artifacts from the existing builder tests (multi-atom, every record kind) | `from_bytes`, then the internal verify checks (call through the crate's existing test hooks; add none to the public API) | the record and field tags, list lengths, string lengths, the digest |

The `artifact` module matters as much as any decoder: it is what prikk will run on artifacts it receives.

## 3. The depths and the triggers (D-2, D-3)

- **The quick depth (the default):** a number of iterations per seed that keeps the whole addition **under
  about 10 s per crate** in a debug build. It runs in every `cargo test`, everywhere.
- **The deep depth:** `BRYGGE_MUTATION_DEPTH=deep` multiplies the iterations (choose and state the factor;
  aim for minutes per crate in release mode).
- **The CI job:** a new workflow `mutation.yml`, or a job in `ci.yml` (say which, and why). It needs:
  - **`on: push` with `paths:`** covering every parser's source (`crates/brygge-decode-*/src/**`,
    `crates/brygge-ir/src/**`), `tools/mutate/**`, `Cargo.lock`, and the workflow file itself; plus
    `workflow_dispatch`. **No `schedule`;**
  - Linux only, stable toolchain;
  - runs the deep depth in `--release` **under a memory cap**: `ulimit -v <N>` in the step's shell, before
    `cargo test`;
  - an explicit `timeout-minutes`.
- **Calibrate the cap honestly:**
  1. pick N so that the clean tree passes with a clear margin (test binaries reserve address space for threads
     and allocator arenas; consider `--test-threads` and `MALLOC_ARENA_MAX`, and say what you chose);
  2. **then prove the cap catches the class:** run once, locally, with the 0.3.0 tree's `ruzstd` 0.7.3 and the
     60 KB input from request 035 fed through the hg module. The run must die, and report the outcome. Do
     not commit anything that uses the old crate.
- **The release cut:** add one step to `docs/src/development/releasing.md`, "Cutting a release", step 1 (the
  preparation): the dev team runs the deep depth locally under the same cap, and records the result in the cut
  request. It is a recorded step of the prep, not a new CI gate.

## 4. Findings

- **Every finding** (a panic, an over-ceiling `Ok`, a time-budget overrun, a memory-cap kill) is reported in
  the request with its saved input.
- **Fix it in this batch if small.** Otherwise report it, and the architect hands it on.
- **Either way, its input becomes a named regression test** in the crate's ordinary tests, so it runs on
  stable everywhere, forever.

## 5. Proof

- The quick depth adds under about 10 s per crate. Report the timing per crate, debug and release.
- **The deep depth,** on the clean tree under the cap: the iterations, the time, and the findings.
- **The cap proof** of §3.
- **The usual gates:** stable and 1.87; clippy on three targets; deny; audit; the isolation check; the
  publish dry-run of six crates; the book; the links.
- **The CI job proven on a topic branch** (it touches CI): push a commit that changes a parser file trivially
  and check that the deep job runs; push one that changes only docs and check that it does not. Then
  fast-forward `main`.
